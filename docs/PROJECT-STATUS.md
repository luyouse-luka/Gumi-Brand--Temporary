Shopify 前端项目（Gumi Brand 官网 + 商品页）。设计交付源为 Figma
`Internal - Gumi Brand & Website` 的 SECTION `401:31719`「Desktop & Mobile MVP (14/08/26)」，
位于 **🟢 READY FOR DEV** 分组下。

**当前阶段：11 个静态页全部落地，四线审计的上线阻断级问题已修完**（Homepage / PDP / Science / Reviews / How Gumi Works /
Our Story / FAQ / Get in Touch / Referral / Privacy Policy / Shipping），
每页 5 个宽度（390/768/1024/1440/1920）无横向溢出、无卡住的入场动画。
改动记录见 [CHANGELOG.md](CHANGELOG.md)。

验证脚本 `tools/shoot.py`（全页截图 + 溢出 + 卡住的 `.wowo`），`python3 tools/shoot.py --all`。
新页面外壳由 `figma/new-page.py` 从 index.html 现切现拼，`--resync` 可把 header 改动推给所有页。
长文案一律用 `figma/dump-text.py` 从节点取全文 —— `build.txt` 会把长字符串截断成省略号。

⚠ **两端要同步做**：手机稿（390）不是桌面稿的等比缩小，数值必须各取各的。第四轮抽查发现
Homepage 有 3 处 mobile 字号是凭手感缩的（已修）。判据是把每个 `@include mobile` 块里的
字号与手机稿实际字号集合对一遍 —— 不在集合里的就是编的。

⚠ **交互态要一起做**（CLAUDE.md 铁律 13）：可点击的地方都要有 hover，状态变化都要走
`transition`。这类要求**既不在 Figma 稿里也不在 build spec 里，没人提就一定漏** —— 第五轮
清点时 19 类可点击元素只有 9 类写了 hover、其中 7 类还没过渡。时长与曲线统一在
`_variables.scss` 的 motion 段（`$t-base` / `$ease-out`），hover 一律用 `@include hover`
包 `@media (hover: hover)`，否则触摸屏点完 hover 态会粘住。
判据是 Playwright 遍历所有 `a[href]` 与 `button`，比对 hover 前后的 computed style。

### 第一三七轮新开的（2026-09-10）— 电话区号的两个自定值

**① 各国号码的示例格式 —— 第一三八轮已按实际位数补齐，剩两个数待定。**

r137 曾共用稿上澳洲那串 9 位数，六个里错了四个（US/CA/GB 少一位、SG 多一位、
NZ 没有 400 号段）。需求方追问后在 r138 改成每国自带 `data-example`：

| 选中 | placeholder | 位数 |
|---|---|---|
| AU | `+61 400 000 000`（稿值） | 9 |
| NZ | `+64 21 000 0000` | 9 |
| US | `+1 201 555 0000` | 10 |
| GB | `+44 7400 000000` | 10 |
| CA | `+1 204 555 0000` | 10 |
| SG | `+65 8000 0000` | 8 |

⚠ **仍待需求方定的是 US / CA 的区号 `201` / `204`**（新泽西 / 曼尼托巴）——
它们是真实区号，纯粹为了让格式合法，**不代表业务所在地**。
要绑到客服所在地，换这两个数即可；`555` 那一段别动，那是北美保留给虚构用途的交换码，
换掉就可能指向真实线路。改完跑 `tools/phonecode.py`，位数断言会守住长度。

**② `--bare` 列表的 `max-height` 是派生值，没有稿依据。**

```scss
max-height: 6 * 40px + 8px + 2px;   // 6 行 x 40 + 列表 4/4 padding + 1/1 border
```

基类的 224 是按**五行**定的；六行要 248，少了就把第六行裁成半截。
⚠ **加第七个国家这个数要重算**，否则那一行又会被裁。
⚠ 末尾的 `+ 2px` 是列表自己的边框（`border-box` 下 `max-height` 含 border）——
少了它正好还差 2px，**肉眼看不出来**，判据读 `clientHeight` vs `scrollHeight` 才抓到。

### 第一三五轮新开的（2026-09-10）— cart 焦点环的取舍，以及一条没内容的需求

**① 需求方第 3 条只有编号没有内容**（消息在 "3." 处截断），未做，等补。

**② `.gb-cart__close` 的焦点环只去掉了"没有手势的那一次"，不是一律去掉。**

需求方的原话是「直接进 `/cart` 时……有 focus-visible 的样式需要去掉」，描述的是
**那个特定场景**。一律去掉只要一行 CSS，但键盘用户从此在这个按钮上看不到焦点落在哪。
所以本轮做的是按场景区分：

| 打开方式 | 环 | 为什么 |
|---|---|---|
| 直接进 `/cart`（无任何输入） | **去掉** | 焦点背后没有用户手势，环描述不了任何东西 |
| 鼠标点购物车图标 | 本来就没有 | Chrome 对鼠标焦点不画 `:focus-visible` |
| 键盘 Tab + Enter 打开，或 Tab 到 close | **保留** | 键盘用户必须知道焦点在哪 |

⚠ **如果需求方要的是"任何情况下都不要这个环"**，改法是把 `.gb-cart__close`
从 `@media (pointer: coarse)` 块里提出来变成无条件规则（一行），
并把 `tools/cartfocus.py` 的第 3 条断言（a11y 下限）一并删掉。
**这是一个可访问性取舍，需要需求方点头，不由我们单方面决定。**
另一条中间路线是照 r81 `.gb-sub__select` 的先例，让 `focus-visible` 画 hover 同款背景
而不是 outline —— 环没有了，键盘指示还在。

### 第一二八轮新开的（2026-09-09）— wowo「刷新像执行两遍」：现象需要需求方确认

**实测测不出**。线上首屏逐帧采了四种场景（1440 冷启动 / 390 暖缓存刷新 / 390 滚到 2600 后刷新），

门控是好的：`<head>` 里同步 `h.classList.add("js")`，`customstyle.css` 紧随其后，都在首次绘制前。

**最可能是浏览器的 paint holding** —— 刷新时保留上一版页面的最后一帧（那时 wowo 已播完、
内容可见），直到新页面首次绘制才换掉，看起来就是「先出现内容，然后又淡入一次」。

放大它的是**空白期**：`window.gumi` 在 4x 节流下 1.5～2 秒才到，这段时间首屏是空的。

**三条路，需要拍板**：

| | 做法 | 代价 |
|---|---|---|
| A（现状） | 不动 | 刷新时仍会看到那一下 |
| B | **首屏元素不挂 `wowo`**（第十四轮做过一次「首屏去 wowo」） | 首屏没有入场动效，但刷新时内容直接在位，"重播"观感消失 |
| C | 让首屏兜底不等 `main.js`（独立小脚本或纯 CSS 入场） | 偏离「统一用 Terra 的 wowo」这条约定，且要自己维护一套 |

**当前按 A（未动代码）。** 先请需求方确认现象是不是「只在刷新时、首次打开正常」——

### 第一二〇轮新开的（2026-09-09）— `gb-science-card__value` 的语义化

**客户原话**：「`gb-science-card__value` 数字不要单独放 p 里，没有任何的语意」。

现在的结构（`science.html` / `index.html` / 线上 `sections/gb-science.liquid:53-58`）：

```html
<p class="gb-science-card__eyebrow">Easy Habit</p>
<p class="gb-science-card__value" data-count-up><span>95%</span></p>
<p class="gb-science-card__text">of users take Gumi at least 4-6x per week…</p>
```

客户指的是三件事：

1. `<p>` 的定义是「一个段落」，`95%` 是一个数值不是段落；
2. **一句完整的话被切成了两个互不相干的段落** —— `95%` 与 `of users take Gumi…`
   合起来才成句，第二段以介词 `of` 开头单独不成立。屏读器读作「95%」→停顿→「of users…」，
   两者关联在语义树上是断的；SEO / AI 抓取拿到两条碎片而非一条统计陈述；
3. 这张 `<article>` 三个 `<p>` 平铺、**没有任何标题**，在文档大纲里是无名节点。

**两种改法**（数字仍是视觉主体，`.gb-science-card__value` 已是 `inline-block`，样式基本不动）：

| | 做法 | 代价 |
|---|---|---|
| A | 合并成一句，数字用 `<strong class="gb-science-card__value">` 做样式钩子 | 要补 `font-weight`（`<strong>` 自带 bold）；**nutrient 变体做不到**，见下 |
| B | 数字提为卡片标题 `<h3 class="gb-science-card__value">` | 要补 `font-weight` 与 UA 字号；需确认页面标题层级不乱 |

**三条动手前必须知道的约束**：

- ⚠ **`data-count-up` 不能留在合并后的 `<p>` 上** —— `main.js` 的 `countUp.run()` 读
  `el.textContent` 去匹配 `^(\D*?)(\d+(?:\.\d+)?)(\D*)$`，合并后整句话匹配不上会直接
  `return`，**数字滚动动画静默失效**（不报错、看不出来）。走 A 要把 hook 留在 `<strong>` 上，
  也就是现在 `<span>` 那一层的位置。
- ⚠ **nutrient 变体做不到 A** —— 它的 `__value` 在 `__body` 内、`__text` 在 `__body`
  **外面**（`<article>` 的直接子，`gb-science.liquid:59-61`），两者不相邻，合不成一句。

### 断点体系（2026-08-25 第二十九轮改制，改之前先读完这一节）

断点分成**两族**。**值档之间必须互斥**，布局阈值可以互相嵌套：

| 族 | mixin | 范围 | 管什么 |
|---|---|---|---|
| 值档 | `@include mobile` | ≤575 | 手机专属微调，叠在 narrow 之上（当前零使用者） |
| | `@include narrow` | **≤767** | 手机稿 390 的数值 + 手机排布 |
| | `@include tablet` | **768–1280** | `fluid()` 插值，没有设计稿 |
| | `@include pc` | ≥1281 | PC。桌面稿 1440 的值写在基础规则里 |
| 布局阈值 | `@include mid` | **≤991** | 卡片网格降一列 |
| | `@include stack` | ≤1024 | 稿里的两栏并排放不下，改上下堆叠 |
| | `@include tight` | ≤1200 | 版心开始吃紧 |

⚠ **值档不许重叠**。第十六~二十八轮的 `narrow`(≤768) 与 `tablet`(576–1280) 重叠了 193px，
胜出方由源码顺序决定，而顺序全站不一致 —— 130 个选择器在两边声明了同一属性，
表现是「同一行字的字号来自手机档、字距来自插值档」。第二十九轮改成互斥后一次性消失。

⚠ **布局阈值只准携带排布，不准携带数值**。`tight`/`stack` 里一旦写 `font-size`/`padding`，
就与 `tablet` 重叠、又把顺序依赖请回来，还会让 `narrow` 的手机值在 768 处硬跳
（`.gb-page-hero__title` 曾在 `tight` 里写死 48px，768 处从 30 直接跳上去）。
数值一律进 `tablet` 的 `fluid()`。**唯一例外是「跟着排布走的几何」** ——
如 `.gb-vs__pile` 的百分比定位：它相对的容器在堆叠时比桌面稿还宽，比例必须跟着布局切换，
且百分比**根本无法用 `fluid()`**（CSS `calc()` 不能用长度除以长度得到无单位进度）。

⚠ **布局阈值不要去对齐 767/1280**。一台 1194 宽的平板放得下稿里的两栏，硬堆成一列是把
好排版改坏；第十六轮第一版就是把 ≤1024/≤1200 全推到 1280，结果 1025–1280 从两栏变单列，
那是**改制引入的回归**。

⚠ **值档的交接必须由 `narrow` → `tablet` 完成，不能由 `mobile` → `tablet`**。
`mobile` 只到 575，而斜坡从 768 起，中间的 576–767 会掉回基础的桌面值 ——
`:root` 的 `--pad-x` 就这样短暂地在 576–767 用了 80px 的桌面留白（屏幕更窄留白反而更大），
第二十九轮修掉。

⚠ 平板数值一律写 `fluid($手机值, $桌面值)`，别拍脑袋填中间数。斜坡区间是 **768 → 1281**，
在 768 处精确等于手机值 —— 所以 `narrow` 与 `tablet` 的交接天然无缝，不需要额外对齐。
`fluid()` 的斜率**必须无单位** —— 写成 `26px * (100vw - 768px)` 是 px×px，量纲错了，
整条声明会被静默丢弃，表现是「字号原地不动、padding 掉回 0」而 DevTools 里那行看着完全正常。
⚠ **`fluid()` 只能用于 px**。百分比不行：CSS `calc()` 不能用长度除以长度得到无单位进度，
百分比量要么跟着排布走（写进布局阈值），要么换算成 px。

⚠ 改完**必须实测**跨宽度的计算值，不能看截图目测 —— 上面那个量纲错误就是目测判成
「已生效」、实测才抓出来的。判据脚本见下方「验证工具」。

### 平滑滚动（2026-08-21 第十七轮定）

用 **Lenis 1.3.11**（MIT），vendored 在 `assets/lenis.min.js`，无构建步骤。
驱动代码是 `assets/main.js` 的 `smoothScroll` 模块。

- **`html { scroll-behavior }` 必须保持 `auto`**。Lenis 内部靠 `window.scrollTo` 落位，
  而按 CSSOM-View，`scrollTo` 是按元素自己的 `scroll-behavior` 执行的 —— 写 `smooth`
  就成了两层平滑套在一起，页面会飘会拖尾。
  老教程里那条 `.lenis.lenis-smooth { scroll-behavior: auto !important }` **自 Lenis 1.3
  起已失效**（不再输出 `lenis-smooth` 类），指望不上。
- **每新增一个 `overflow-y: auto` 的容器，就要登记进 `smoothScroll.PREVENT`**，
  否则 Lenis 把滚轮全吃掉、那个容器再也滚不动。现有三个：
  `.gb-product__thumbs`（只在桌面可滚）/ `.gb-header__panel`（只在手机可滚）/
  `.gb-nl-panel__body`。`tools/rwd.py` 逐视口盯这条 —— **单一视口验不全**。
- 触摸不接管（`syncTouch: false`），真机原生惯性比任何模拟都好。
- 两条关闭路径：`prefers-reduced-motion: reduce` 自动不启用；`<html data-no-smooth>` 手动关。
- 弹窗打开时 `lenis.stop()`（`modal.open` 里调），页面已被 `is-modal-open` 锁住，
  弹窗正文才滚得动；关闭时 `start()`。
- 站内锚点走 `lenis.scrollTo`，**不开 Lenis 自带的 `anchors`** —— 站里有 70 个
  `href="#"` 占位链接，交给它有把页面拉回顶部的风险。

  这层——`.gb-scallop` / `.gb-scallop--lg` 本来就自给自足，直接读 `:root` 的
  `--sc-w/h` 或 `--sc-lg-w/h`）。section 只需要做一件事：把 `var(--sc-h)` 或
  `var(--sc-lg-h)` 加进自己的 `padding-bottom`（`calc(原值 + var(--sc-h))`），
  给波浪腾出一条自己的高度。多数模块「永远大瓦片」或「永远小瓦片」，直接把变量
  写死进 `padding-bottom`；同一个 class 在不同页面要求不同瓦片的（`.gb-page-hero--center`
  / `.gb-product` / `.gb-app-section` / `.gb-ingredients`），新增了 `--lg` 正交修饰类
  （`.gb-page-hero--lg` / `.gb-product--lg` / `.gb-app-section--lg` / `.gb-ingredients--lg`，
  跟 `.gb-scallop--lg` 是同一种命名思路，只覆盖 `padding-bottom`）。
  ⚠ **`position: relative` 也要自己补**——之前是 `.gb-sec-edge` 给的，删掉那层之后
  每个用到 `.gb-scallop--edge` 的 section 都要自己有这条，否则波浪的 `position:absolute`
  飘到更外层的定位祖先上去。
- 配色约定：`--wave-bg` 恒为**上方**那块的颜色、`--wave-fg` 恒为**下方**那块；
  `--down`（弧朝下）与 `--lg`（大瓦片）是两根正交的轴。
- ⚠ **不要写 `section + .gb-scallop` 这类相邻兄弟选择器** —— Shopify 给每个 section 套的
  `<div id="shopify-section-…">` 一来就全失配。（现在波浪在 section 内部，本来也不需要。）
- 页脚两道（`.gb-footer-cta-wrap` / `.gb-footer-wrap`）是**上边缘**、在流里，
  本来就在自己模块内，没有改；要做上边缘变体再加一组 `--edge-t`。

⚠ **改波浪尺寸机制或搬波浪时，路径式的 computed-style diff 无效**（节点一移动，
后面所有兄弟的下标整体错位，diff 比的是不同元素）。判据要换成与位置无关的不变量：
「波浪顶边到上方内容底边的间距」==该模块原来的 `padding-bottom` 数值、波浪底边
贴 section 底边（像素差 ≤0.6）、波浪宽度贴 section 宽度。脚本见 CHANGELOG 第二十三轮。

### 入场动效

**除下方「特殊动效」列出的以外，所有 fadeIn / fadeInUp 一律用 `wowo`，且尽量靠 class 控制。**

- 移植 Terra 的两份文件：`project/Terra/assets/scss/helpers/_animation.scss`
  + `script.js` 的 `morph.wowoSetup()` / `morph.wowo()`。不新写 IO 观察器、不引 AOS / animate.css / WOW.js。
- 用法：元素加 `class="wowo fadeInUp"`，错峰加 `delay-in-N`（N=1~20，每级 0.1s）。
  **写 HTML 时直接把 class 挂上**，不要在 JS 里逐个查询注入 —— 只有 CMS 导出不可改的 HTML
  才走 `wowoSetup()` 的选择器映射表。
- 可用动画名：`fadeIn` / `fadeInUp` / `fadeInDown` / `fadeInLeft` / `fadeInRight` /
  `zoomIn` / `zoomOut` / `bounceIn`；时长固定 0.7s，fadeInUp 位移 30px；**只播一次不可重播**。
- ⚠ 隐藏门**不再是无条件的**（第十四轮改）：规则是 `html.js .wowo { opacity: 0 }`，`js` 类由
  `<head>` 的内联脚本加、并在 `load`（或 4s 兜底）时若 `window.gumi` 不存在就摘掉。
  **只加 `js` 类是不够的** —— 那行内联脚本在 main.js 404 / 顶层抛异常时照样执行，门照样成立；
  必须以「main.js 的收尾导出存在」为条件。改加载顺序后仍要验首屏 opacity 回到 1。
- ⚠ **动效 class 挂在包裹容器上，不挂在 `<img>` / `<picture>` 上**（第十七轮）：
  `<picture>` 当不了定位/动效元素（默认 inline，改 display 又会把 `<source>` 提升成布局项），
  且图片自己常带 `transform`（如 hero 小熊的 7.92° 倾斜），两者叠在同一个元素上会互相覆盖。
  是 `<picture>` 就用一个 `<div>` 包起来，class 挂 div。
- ⚠ **首屏元素不挂 `wowo`**（第十四轮）：合成层上的 opacity 动画不产生 LCP 候选，
  要等 1500ms 移除 class 才登记，11 页 LCP 因此卡在 ~1550ms。折线以下照常用。
