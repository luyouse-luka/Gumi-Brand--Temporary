### ⚠ 这张表推翻了交接文档 5 节「已知风险点」第 3 条的因果链

交接文档写「无错误边界：任一模块抛异常会中断后续模块初始化 →
**这条直接关系到 `.wowo` 的永久不可见风险**」。实测：

- 级联是**严格单向**的 —— 故障点在第 N 个模块，死的是第 N…8 个，第 1…N-1 个完好。
- `wowo.init()` 排在 `ready()` 回调的**第一行**（`main.js:623`），且它先注册监听再跑一次
  （`main.js:54-56`）。所以**模块 2-8 里任何一个抛异常，`.wowo` 都照常回到 opacity 1**
  （实测 27/27，7 组全一致）。
- 「内容永久不可见」的真实入口只有三个：**wowo 自身抛异常**、**`main.js` 没加载成功**、
  **`main.js` 顶层就抛**。前者由 P0-2 放大，后两者由 P0-1 兜不住。

无错误边界仍然是缺陷（P1-3），但它的后果是「后半段功能静默消失」，不是「整页白屏」。

## 2. 真缺陷

### P0-1 `<noscript>` 兜底覆盖不到「JS 加载了但失败」，全站内容永久不可见

**位置**
`assets/scss/helpers/_animation.scss:16-17`（`.wowo { opacity: 0 }` 无条件）
· `assets/js/main.js:11-13`（合约注释本身已点出，但没落到实现）
· 11 个 HTML 的 `<noscript><style>.wowo{opacity:1 !important}</style></noscript>`

**现象**
`<noscript>` 只在**脚本被禁用**时生效。脚本能跑但失败的两种真实情况——
资源 404（`?v=` 改错、Shopify 资产路径变了、CDN 抖动）和脚本顶层抛异常
（打包出错、语法错、第三方脚本污染原型）——`<noscript>` 一条都挡不住。

**判据**（`p3b.py`）

| 场景 | `.wowo` 可见 / 总数 | 判据 |
|---|---|---|
| 健康参照 | **27 / 27** | — |
| JS 关闭（`java_script_enabled=False`） | 27 / 27 | 截图 `s_jsoff.png` vs `s_ref.png`：**平均绝对像素差 0.00，差异 >16 的像素 0.00%** |
| `main.js` 请求被 abort（模拟 404） | **0 / 27，全部 opacity=0** | `routeHits=1`，`window.gumi=false` |
| `main.js` 顶层 `throw` | **0 / 27，全部 opacity=0** | pageerror = `AUDIT top-level fault`；截图 vs 参照 3.97% 像素差 |

**建议**
把隐藏条件挂到「JS 活着」这件事上，而不是无条件：
`<head>` 里内联一行 `<script>document.documentElement.classList.add('js')</script>`，
CSS 改成 `html.js .wowo { opacity: 0 }`。这样脚本没加载/没执行 → 规则根本不成立，
`<noscript>` 那条 `!important` 也可以退休。这一步做完，P0-2 与 P1-3 的最坏后果都从
「白屏」降级成「没有入场动画」。

### P0-2 wowo 的 rAF `ticking` 闩锁不可复位：一次异常 = 滚动入场永久停摆

**位置** `assets/js/main.js:43-52`

```js
var ticking = false;
var onScroll = function () {
  if (ticking) return;
  ticking = true;
  window.requestAnimationFrame(function () {
    self.run();        // ← 这里一抛
    ticking = false;   // ← 这行永远到不了
  });
};
```

**现象**
`self.run()` 只要抛一次（哪怕是瞬时的、后续完全健康），`ticking` 就永远停在 `true`，
之后每一次 scroll / resize 都被第一行 `if (ticking) return` 挡掉。
配合 `.wowo{opacity:0}`，尚未入场的元素**永久不可见**。

**判据**（`p10_latch.py`，给 `window.gumi.wowo.run` 装调用计数器，control / fault 两组对照）

| | `run()` 被调用次数 | 抛出次数 | `.wowo` 总数 | 卡在 opacity<0.5 |
|---|---|---|---|---|
| control（无故障，全程渐进滚动） | **23** | 0 | 27 | **0** |
| fault（只让第 2 次调用抛一次） | **2（此后冻结）** | 1 | 27 | **22** |

同一现象在 `p3b.py` 的 D 组独立复现过一次（23 个卡住）。
注意 `slider`（`main.js:436-438`）和 `gallery`（`main.js:577-579`）的同类 rAF 节流
**把 `_t = 0` 写在业务调用之前**，所以没有这个问题——只有 wowo 写反了。

**建议** 一行改动：
```js
window.requestAnimationFrame(function () {
  try { self.run(); } finally { ticking = false; }
});
```

### P1-3 单 IIFE 无错误边界，模块 N 抛异常 → 第 N…8 个全部静默消失

**位置** `assets/js/main.js:622-631`

**现象** 见上面爆炸半径表。级联本身是真的，只是后果被 `wowo` 排第一救了一半。
最刺眼的一组：往 `bear-meter`（第 3 个）注入一次异常，**页面上没有任何报错提示**，
但下拉菜单之后的 popText / 弹窗 / 轮播 / gallery / 表单预选**全部不工作**，
用户只会觉得「点了没反应」。

**判据** `p2_blast.py`，9 组（8 模块 + 对照）× index，另 4 组 × get-in-touch。
每组只产生 1 条 pageerror，页面其余部分照常渲染 —— 也就是说**故障是完全静默的**。

**建议**
```js
[["wowo",wowo],["header",header],…].forEach(function (m) {
  try { m[1].init(); } catch (e) { /* 开发期 console.error(m[0], e) */ }
});
```
成本一行，收益是把「后半段功能全丢」降级成「一个模块丢」。

### P1-5 resize 会把 reels 轨道的横向位置甩回居中（移动端 toolbar 收放即触发）

**位置** `assets/js/main.js:504-520`
```js
var relayout = function () { fill(); centre(); sync(); };
window.addEventListener("resize", relayout, { passive: true });
```
`centre()` 里 `jump()` 无条件写 `track.scrollLeft`（`main.js:396-401` / `514`），
既不判断用户是否已经滚过轨道，`relayout` 也没有节流、没有「只在宽度变化时才重排」。

**现象** 移动端地址栏收放只改高度，浏览器照样派发 `resize` ——
用户刚横向滑到第 4 个 reel，一竖滚就被弹回中间。（对应 memory
`mobile-toolbar-resize-rebuild`：真凶从来不是浏览器，是自家 resize 无条件重建。）

**判据**（`p5_interact.py` 5.1）
把轨道滚到 `scrollLeft=1072`，只把视口从 `1440×900` 改成 `1440×760`（宽度不变）：

```
before = 1072   →   afterHeightOnlyResize = 1728   （moved: true）
```

**建议** 记住上一次的宽度，`if (w === lastW) return;`；`centre()` 只在初始化时跑，
或加一个「用户动过轨道就不再自动居中」的标志。

### P1-6 `fill()` 的克隆数量没有上界，pitch 退化时会造出上千个节点

**位置** `assets/js/main.js:376-394`
```js
var need = Math.ceil(2.5 + track.clientWidth / Math.max(1, setWidth()));
```
`Math.max(1, …)` 把「一整组宽度为 0」兜成 1px，于是 `need` 直接变成视口宽度的数量级；
`while (have < need)` 没有任何上界。

**判据**（`p7_harness.py` / `p8.py`，独立 harness 页直接 `<script src=…/main.js>`）

| 场景 | 每组 3 个 slide 时的轨道子节点数 |
|---|---|
| 正常（slide 200px + gap 16px） | 15（5 组） |
| slide 宽 0 + gap 16px | **99**（33 组） |
| slide 宽 0 + gap 0 | **4281**（1427 组，`need = ceil(2.5 + 1440/1) = 1443`）；`domNodes` 4290 |

**现状** 站上 4 个 slider 的 `.reel` 都是 CSS 定宽，实测轨道 20 个子节点（1440）/ 15（390），
没有触发。属**潜伏**缺陷：进 Shopify 换成产品图后，图片没加载完 + 没有 `width/height`
属性 → 首帧宽度为 0，正好落进这条路径。

**建议** `if (setWidth() <= 1) { return; }` + `need = Math.min(need, 12)`；
或者把 `fill()` 推迟到轨道内图片 `decode()` 之后。

## 3. P2（健壮性 / 可访问性 / 清理）

### P2-7 同时打开两个弹窗会留下一个关不掉的全屏遮罩
**位置** `main.js:274-297`。`open()` 不关旧的（`main.js:275` 只挡「同一个」），
`close()` 只认 `this.current`（`main.js:289-290`）。
**判据**（`p6_edge.py` 6c）：`open(reel-video)` 再 `open(nutritional-label)` →
两个都 `is-open`，reel-video 还挂着 `aria-hidden="false"`，`current` 已指向后者；
按 Esc 只关掉后者，**reel-video 留在屏幕上**（`afterEsc_rvStillOpen: true`），
而 `current` 此时是 null，再按 Esc / 点它的遮罩都进不了 `close()` 的主体。
滚动锁也被解掉了（`afterEsc_scrollLock: false`），页面能滚但被遮罩盖着。
**现状** 当前 markup 用户到不了（第一个弹窗的遮罩盖住了所有触发器），纯潜伏。
Shopify 阶段一旦加第二个弹窗（尺码表 / 订阅说明 / 视频）就会显形。
**建议** `open()` 首行加 `if (this.current) { this.close(); }`。

### P2-8 `e.target.closest` 无守卫，document 上的合成 click 直接抛异常
**位置** `main.js:256`
**判据**（`p9_final.py` 4）：`document.dispatchEvent(new MouseEvent('click',{bubbles:true}))`
→ pageerror **`e.target.closest is not a function`**。
Shopify app、cookie 弹窗、分析脚本在 `document` 上派发合成事件很常见。
**建议** `var t = e.target; if (!t || !t.closest) { return; }`

### P2-9 popText 的 catch 摘掉的正是 CSS 兜底所依赖的钩子
**位置** `main.js:152` 对 `assets/scss/components/_motion.scss:107-111`
```js
try { this.split(els[i]); } catch (e) { els[i].removeAttribute("data-pop-text"); }
```
CSS 的兜底是 `[data-pop-text]:not(.is-split) .pop-word { opacity: 1 }` ——
catch 把 `data-pop-text` 摘了，选择器就失配，刚建出来的 `.pop-word` 落回 `opacity: 0`。
**判据**（`p8.py` B / C）：让 `split()` 在最后一行（`classList.add('is-split')`）抛异常 ——
- 同时屏蔽 IntersectionObserver：63 个 `.pop-word` **全部 opacity 0**（`attrStillThere: 0`）。
- 保留真 IO：IO 照样给 4 个宿主加 `is-popped`，63 个词全部可见（`invisibleWords: 0`）。

所以实际有 IO 兜底，**当前不会真的翻车**，但 CSS 那层兜底等于是死的，
且属性被摘掉会让将来的重初始化（Shopify section 重载）跳过这些元素。
**建议** catch 里不要动 `data-pop-text`；要标失败就另加 `data-pop-failed`。

### P2-10 跨断点开着抽屉后，桌面端下拉面板卡在展开态
**位置** `main.js:74-104`（`set()` 只被点击 / Esc / 外部点击驱动，没有断点复位）
**判据**（`p6_edge.py` 6a）：390 打开抽屉 → 视口拉到 1440：
`body.is-menu-open` 仍在、`.header.is-open` 仍在、`.header__panel` 的
`grid-template-rows` = `258px`、实测高 **259px**、`aria-expanded="true"`。
**页面还能滚**（`scrollY` 成功到 800，`body` 的 `overflow-y: auto`）——
因为 `_header.scss:391-393` 的锁被 `@include mobile` 圈住了，所以不是锁滚动 bug，
是一块 259px 的空面板挂在桌面视口上。
**建议** `matchMedia('(max-width: …)').addEventListener('change', () => self.set(false))`。

### P2-11 Esc 关抽屉不复位二级折叠项
**位置** `main.js:78-80` + `86-96`
**判据**（`p5_interact.py` 5.8）：展开一个 `[data-collapsible]` → Esc 关抽屉 →
`afterEsc_open: false`（抽屉关了）但 `afterEsc_collapsibleStillOpen: true`、
子项 `aria-expanded` 仍是 `"true"`。下次打开抽屉，子菜单是展开的。
**建议** `set(false)` 里顺手清掉所有 `[data-collapsible].is-open` 与其 `aria-expanded`。

### P2-12 tablist 不支持方向键，也没有 roving tabindex
**位置** `main.js:307-322`
**判据**（`p5_interact.py` 5.4）：焦点落在 `#nl-tab-info` 按 `ArrowRight` →
`aria-selected` / `tabpanel.hidden` / `tabindex` **三项全部不变**（`arrowWorks: false`）；
两个 tab 的 `tabindex` 都是 `null`（无 roving）。点击路径的 aria 同步是**正确**的
（`afterClick`: `selected=[false,true]`、`hidden=[true,false]`）。
**现状** 可用（两个 tab 都在 Tab 序里，Tab+Enter 能切），只是不符合 WAI-ARIA Tabs 模式。

### P2-13 `FOCUSABLE` 名单漏 `iframe` / `video[controls]` / `audio[controls]` / `summary` / `[contenteditable]`
**位置** `main.js:246`

### P2-17 gallery 的 `slide.offsetLeft - stage.offsetLeft` 依赖 stage 不是定位元素
**位置** `main.js:569`
**判据**（`p5_interact.py` 5.6）：当前 `stage.offsetLeft = 0`，且 slide 与 stage
**共用同一个 offsetParent**（`offsetParentSame: true`），减法恰好等价于「slide 相对

**建议** 改成 `slide.getBoundingClientRect().left - stage.getBoundingClientRect().left + stage.scrollLeft`。
